# Refutation: RISO/CAM Retrospectives

*Method: I re-derived the load-bearing claims against the tree rather than against the archaeology. Counts below are from `grep`/`awk` on the actual files; image claims from PIL mode/chroma inspection; timing claims from `lan-diag.log`.*

---

## 1. Claims that are factually wrong

### E1 — The `exportSeparations` uniform count is 64, not 81

`awk 'NR>=976 && NR<=1105' js/save.js | grep -c 'gl\.uniform'` → **64**. Against 120 in `renderer.js:1144-1458`.

The pipeline archaeology asserts 81 (§S1) and the **product critique repeats it verbatim** (§6). The architecture critic is the only one who counted. This matters beyond pedantry: the headline "drifted by 17 uniforms" was computed against a denominator two of three critics never checked, and the true gap is 56 calls, not 39. A review whose central artifact is *"nobody verified this"* propagating an unverified number through two documents is not a small irony.

Same pattern: `mode==='flat'||'stipple'` sites are **22** (architecture) not 16 (archaeology, repeated by product).

### E2 — "No scanned or photographed counterpart of any test print exists anywhere in the tree — I searched"

Product critique §1. False as stated. `captures/` contains `test_02_black.png`, `test_03_gray50.png`, `test_04_gray25_75.png`, `test_06_step_wedge.png`, `test_07_isolated_dots.png`, `test_08_calibration.png`, plus `captures/tone_curve.txt` — a 17-point table headed *"Input gray (0-255) → measured ink coverage (%) from RISO Grain Touch"* — plus four annotated crops under `docs/validation/`.

The **substance** survives and I'll grant it: I checked these — all are 8-bit `L` mode, max chroma 0, dimensions unrelated to the 7016×9921 targets, i.e. downsampled decodes of the `.prn` raster, not photographs of paper. So they measure what the driver *sends*, not what the paper *does*.

But "the validation loop never closed" is too strong for what is actually there. There is per-patch ink-area ground truth (`stats.json`: `wedge_step_0.ink_area_fraction`, `solid_black_band = 1.0`), the FM tone curve was fit to it, and `DRIVER_LUTS[4]` cross-validates against it to three decimals. The loop closed on **coverage** and not on **colour**. That is a materially different — and much more interesting — finding than "nothing was ever measured."

### E3 — The linear Black LUT cannot cause "gray goes blue"

The colour critique (§1.2, defect #4) asserts the linear Black profile is *"precisely the 'gray goes blue' pathology… the solver recruits Blue for darkness Black can't deliver."*

Mechanically impossible. `renderer.js:1361`:

```js
gl.uniform3f(inkLocs[i], lt[4][0], lt[4][1], lt[4][2]);   // ← the ONLY thing NNLS sees
gl.uniform3f(lutALocs[i], lt[0]...);  // :1362-1365 — consumed by lutBlend during RENDER
```

`nnlsDecompose` receives ink *endpoints* only. The intermediate knots go to `u_lutA..u_lutD` and are read exclusively by `lutBlend` in the compositing stage. The solver never observes the LUT's shape, so its shape cannot bias ink recruitment. And Black's endpoint is `0.030` — the darkest in the entire table; at `w=1` it delivers more darkness than any other ink.

Two genuine, unrelated defects (the linear knots; the NNLS-chord-vs-render mismatch) have been welded into one false causal narrative, and it is the narrative the retrospective uses to rank the finding as "high."

### E4 — "There was never an executable definition of correct output" / "no test files anywhere"

Architecture critique §1 headline. `selftest.html` (179 lines) drives the real app in an iframe through all six modes, spot separation, paper, PNG export and a forced context loss, with `PASS`/`FAIL`/`SKIP` verdicts, a 240 s boot budget, and beacon streaming. It emits a **numeric per-mode signature**. Verified running, twice, on two GPUs:

```
lan-diag.log:470  SELFTEST PASS  mode GRAIN — variant full, mid-strip luma 133
lan-diag.log:472  SELFTEST PASS  mode RISO  — variant full, mid-strip luma 137
… all six modes …
lan-diag.log:586  SELFTEST PASS  mode LETTERS — variant slim(LINES+RISOMTX), luma 125, rebuild 62s
```

The critic's own §1 concedes `selftest.html` "is 80% of this harness." The defensible claim is narrower and much less dramatic: *there is no pixel-exact oracle, and the smoke suite arrived in July rather than March.* As written, the headline is false, and it is the headline the entire critique is ranked from.

### E5 — "Delete `sw.js` and `manifest.json`; cost is negative"

Product §5. Not negative. `css/main.css:5` and `js/phone.js:633-635` both branch on `display-mode:standalone/fullscreen`. Deleting the manifest removes installability, which is the only way the camera UI gets the chrome-less full-screen layout it is designed around.

And the "21 cache bumps for a cache that never hits" indictment overstates blast radius by an order of magnitude. `index.html:3509`:

```js
if('serviceWorker' in navigator && !/\.neocities\.org$/.test(location.hostname)) navigator.serviceWorker.register('sw.js')…
```

In production there is **no service worker at all**. The `ignoreSearch:false` defect is a localhost-only bug. (The dead blob-SW at `phone.js:717-723` is real and does fire the CSP report — that part survives.)

### E6 — "The opaque crossfade tints uncovered paper" is presented as universal and unrecognised

It is neither. `index.html` gates it per layer:

```glsl
float layerTrans = layerIdx < 0.5 ? u_transparent0 : … ;
if (u_dbgNoOpaque > 0.5 || layerTrans > 0.5) { blended = transparent; }
```

and `js/data.js` flags `transparent:true` on Clear Medium and all four Process inks, with a comment naming the exact failure mode: *"blue (C+M) would tint purple from Magenta's RGB."* The defect is real for the ~30 spot inks and already fixed for the process set, deliberately, with the reasoning written down. Reporting it as an error the author didn't see misrepresents the file.

## 2. Hindsight bias

### H1 — "Shader in its own file: wrong from day one, cost one hour"

Architecture §4. Right about the end state, wrong about the day. On day one there was no deploy script (`deploy-neocities.sh` is a July artifact), no build step, and the distribution mechanism was literally `1e9b2fb` *"Add files via upload."* Extracting the shader buys you either **(a)** a build step on a project whose entire deploy is drag-and-drop — killing the one property that made 37-commit days possible — or **(b)** a runtime `fetch()` inserting an async round-trip in front of `initGL`, on the exact platform where boot already costs 34 s, later constrained by a `connect-src 'self'` CSP.

The decision became wrong around `d087406` (March) — which is precisely where the same critic's own thesis says the constraint changed. The critique states the correct trigger point in §1 and then ignores it in §4.

### H2 — "Three backings instead of one — one extra afternoon on the same rig"

Science §3. **There was no rig.** `js/data.js:7`: *"Calibration data from **txtbooks** risograph color swatch scans (2019/2020)."* Third-party dataset, acquired, not produced.

And everything the author demonstrably printed is monochrome. I checked all eight targets: `test_prints/*.png` are 8-bit `L` mode, max chroma **0**. All eight `.prn` captures carry an identical driver-settings header (`stats.json → format.driver_settings_header`, "identical across all 8 files") and classify as single-drum Grain-Touch. `captures/*` likewise `L` mode.

A risograph prints one ink per drum per pass. A 3-backing chart across 28 inks is 28 drum swaps plus registration passes — on drums for which there is no evidence in the tree. The proposal is off by two orders of magnitude in effort and is plausibly infeasible at any budget available to this author. The same objection retires the "measure the palette, not the ink set" fallback: even C(2,2)=1 overprint pair needs two drums.

This is the single largest hindsight error in the three critiques, because §1's entire thesis ("the referent was wrong") rests on the referent having been obtainable.

### H3 — "One afternoon of pointing the camera at a printed step wedge"

Product §1. Same drum problem, plus one the critic manufactures: photographing a wedge with the app's own camera makes an **uncalibrated phone sensor under an unknown illuminant** your ground truth. The science critique — working from the same evidence base — measures that path at mean ΔE00 3.07 with **max 17.8**, only 32% of patches under 2, and degree-4 polynomial correction blowing to **57 ΔE** under exposure drift. One afternoon of phone-photographing a wedge would have produced a *noisier* referent than the ink-area decode already sitting in `docs/validation/`. The two critiques argue opposite sides of this and neither notices.

### H4 — "WebGPU should have stopped at `ce9a9ec`; the problem was solved and verified"

Product §2, echoed by platform §4.4. Refuted by their own log. The post-fix Intel UHD selftest is a **warm-shader-cache** run:

```
lan-diag.log:678  1158ms link:ok +71ms
lan-diag.log:697  13618ms link:ok +221ms      (flat)
lan-diag.log:711  25639ms link:ok +339ms      (screen)
lan-diag.log:725  38632ms link:ok +982ms      (lines)
```

The cold run, same machine:

```
lan-diag.log:539  "768ms link:submitted","28514ms link:ok +27745ms"
lan-diag.log:576  87164ms link:ok +55752ms
lan-diag.log:586  … rebuild 62s   (LETTERS)
```

There is **no post-`ce9a9ec` cold measurement anywhere in the log.** "Solved" therefore means "solved on the second visit, backed by an evictable per-site D3D shader cache." A 28-second white screen on first load plus tens of seconds on each first mode switch is a live product defect, and a defensible reason to keep going. The critics graded a first-visit problem using second-visit numbers.

## 3. Proposals that would have been worse

### P1 — Golden images in March

Architecture §1: 18 reference PNGs, pre-commit, "one day in March." In March the screen dot engine was between architectures **1 and 2 of 7**, ASCII between **v1 and v6**, the paper substrate on **generation 2 of 5**, the separation engine on **generation 2 of 4**. Every one of those rewrites was *designed* to change every pixel.

An 18-image golden set is then 18 files to re-bless on ~28 FIDELITY commits, on every look revert (`521502d`, "user pick"), and on both DPI reversals. That is not a safety net; it is a ratchet aimed directly against the project's operating method ("the output is the specification"). The correct instrument for a moving look is a *directional scalar* — strong-pixel count, mid-strip luma, mean ΔE — which is exactly what 82 `Verified:` blocks contain. The critique documents the winning form (`d5b75b8`: asymmetric glyphs at 4× zoom) and then recommends the losing one.

Golden images become correct when the look stops moving. That is roughly July. That is when `selftest.html` appeared. The timing was not an accident.

### P2 — "Ship three modes; letters and stipple are presets"

Product §3. This mistakes shader-level identity for product identity. LETTERS is `u_mode==1 + u_stampShape=5` **and** a dedicated anchor-tone bake pass (`u_asciiTonePass=1`, 3×3 quadrants), a Canvas2D glyph atlas with tofu detection, a word strip, a curve strip, a sentence sub-mode, and phone controls. STIPPLE is `u_mode==3 + u_amtCrisp` **and** an entirely separate master generator (`StippleCore` Poisson sampler, display-resolution masters, LIVE frame-pool playback on its own `setInterval`).

Demoting them to presets deletes two `_SLIM_GROUPS` entries and nothing else. Every line of prepass, worker and UI stays. And the claimed S2 saving is illusory: S2 is caused by **two prepass engines sharing one flag**, and a "preset" does not merge the engines. The actual fix for S2 is two flags — two lines.

### P3 — "Rewrite `calBlend` as a port of `sep-lut-worker.js` — a much smaller job than it looks"

Science §"what to preserve" #2. Note what the port costs. `sep-lut-worker.js:63-79` replicates the shader's slot-positional chain (`inkAbsorb = 0.9+0.3·slot/3`, `layerDeplete·slot`) **precisely because its job is to invert the shader**. Port it into the shader and the sep-LUT bake — the project's single largest measured accuracy win, ΔE 21.6 → 8.95 — is invalidated wholesale and must be re-derived from scratch, along with the four per-ink area windows and their fitted RMSEs. This is a two-campaign change sold as a refactor.

### P4 — "One state object, folded into `d087406`, half a day marginal"

Architecture §3. `d087406` is a 7,357-line single-commit split whose immediate fallout was `02f2ffb` — the camera was broken by the split and needed a cross-module `R.` prefix audit. Adding a simultaneous 140-global-to-one-object migration compounds the two highest-risk refactors in the project's history into one unreviewable change, **in a repo with no tests** — which is the same critic's §1 complaint. Sequencing them was correct, not lazy.

### P5 — "When WebGPU goes live, set `_isD3D = false`"

Platform recommendation #10. Actively dangerous as written. `_isD3D` also drives `_sepLutMinInk = 1` (`renderer.js:175`), and every export still runs WebGL (`webgpu-live.js:413`, `save.js:130`). Clearing `_isD3D` while the WebGPU overlay is live leaves the export path attempting to link the **full** megashader on the one machine that provably cannot link it — reintroducing the whole-browser freeze the campaign exists to prevent. The recommendation names the correct alternative (`_slimNeeded`) in a parenthetical and then discards it.

## 4. Generic best practice that doesn't fit the context

**G1 — "No `package.json`, no test files."** True, and a design position. This is a zero-dependency, zero-build, classic-script project deployed by copying files to a host that rejects `.wasm`. Adding npm to satisfy a convention imports a lockfile, a `node_modules` tree and a supply chain into a project whose sole build artifact is produced by a 91-line script with two vendored blobs. The one place a build genuinely earned its keep (`build-wgsl.mjs` + a deploy-time abort) is the decision the same critic calls the best in the project.

**G2 — Content-hashed assets.** Fixes a ~1.6% error rate (3 missed bumps across 183 revisions) whose failure mode is self-announcing and self-correcting within one commit. It requires the deploy script to rewrite `index.html` — which makes deployed HTML differ from tracked HTML, while the WebGPU staleness gate hashes `<script id="fs">.textContent` against a build-time hash of the file bytes (`webgpu-live.js:229` vs `build-wgsl.mjs:33`). Inserting a deploy-time HTML rewrite into that pipeline is how you *manufacture* more S7-class silent failures.

**G3 — "Undo covers ~10% of render state."** For a tool whose interaction model is drag-a-slider-look-drag-it-back, a 20-field undo that always restores mode/inks/profile and never restores a half-baked GPU master is a product choice. No critic asked whether a user wants per-plate misregistration on the undo stack.

**G4 — The ISO chart-design programme.** ISO 13655 patch sizing, ISO 12642-2 randomisation, ECI2002 nesting, IT8.7/5 neutral weighting, root-polynomial correction, repeat patches as a drum-banding estimator, and a peer-reviewed publication. Every item is right for a colour-management lab and none of it is a next step for one person with one drum. `INK-PHYSICS-PLAN.md`'s own scope warning — *"This can absorb unlimited effort… resist bundling 1b into it"* — is better calibrated than the advice being handed to it.

Only layer 3 is dormant. The sentence conflates the shipped mitigation with the dormant port to make the thesis land.

## 6. What survives

Ranked by (verified) × (cost to fix):

**One-line defects, verified, fix today:**

1. **`window._saving` is permanently `undefined`.** `state.js:242` declares `let _saving`; `ui-controls.js:823` reads `window._saving`; `webgpu-live.js:412` reads the same flag *correctly* (`typeof _saving !== 'undefined' && _saving`). The stipple LIVE timer therefore keeps rebinding units 9–12 mid-export. Verified, one line.
2. **`window._recordingNow`** — read at `webgpu-live.js:412`, assigned **nowhere** in the tree (`grep -rn` across `js/` and `index.html` returns exactly that one read). Real flag is `isRecording`. One line.
3. **`u_amtJitter` stale during separations.** `renderer.js:576` inits it to `1.0`; `:1279` is the *only* conditional write (`_saving ? 0.0 : 1.0`) and `exportSeparations` never calls `setRenderUniforms`. The one export that reaches a drum keeps the stochastic taps. Verified end-to-end.
4. **S2 — shared `_amtPrepassRunning` with mode-asymmetric requeue.** `renderer.js:2499` requeues only if `_mode === 'flat'`; `:2862` only if `_mode === 'stipple'`; `ui-controls.js:640-645` invalidates and schedules across the boundary. Reachable, verified by reading both `finally` blocks. Two flags, two lines.
5. **`mode` / `window._mode` desync is not hypothetical.** All three critiques call it a latent hazard. It already exists: `js/source.js:1266`, `pdfApplySettings()` writes bare `mode=s.mode` with no `window._mode` update and no `setMode`. (`phone.js:60` and `undo.js:46` are both safe — I checked; `phone.js` follows with `R.setMode`, `undo.js` is guarded by `s.mode !== mode`.) This is the one place the critiques *understated* the problem.

**Structural, verified, real work:**

6. **The uniform fork.** Real, 64 vs 120, and the fix is the right one — parameterize `setRenderUniforms` and delete `save.js:976-1105`. Closes items 3 and half the preview/export divergences.
7. **The Yule–Nielsen identity.** Verified in the shipped stage 4: `paperYN = sqrt(result); inkYN = sqrt(safeInk); transparent = (paperYN·inkYN^d)²` ≡ `result·ink^d`. Genuine. Note the mitigating fact the critique buried: the *correct* form sits 40 lines above it in the same function, behind `u_dbgYNArea`, including the `transmit = ink / safeP` normalisation that fixes the paper-counted-*n*-times error. The fix is a default flip plus re-tuning, not a rewrite — and that reframes it from "the author didn't understand YN" to "the author built the right thing and didn't default to it."
8. **Nine ink LUTs are linear ramps labelled "measured", Black included.** Verified arithmetically (Lagoon R: t = 0.100/0.298/0.500/0.697; Black: 0.105/0.307/0.518/0.720). The **fix survives** — a `provenance:` field plus a startup assertion that any ink claiming measurement has non-zero second difference, ~30 minutes. The **causal story attached to it does not** (E3).
9. **Paper knot hardcoded `0.910/0.912/0.908`**, and `_calLutKey` (`renderer.js:2001-2007`) keyed on ink names only, so changing paper never rebakes. Real, cheap, and it is the defect most visible to a user on coloured stock.
10. **`manifest.json` `start_url:"/"`** against a `/risocam/` deploy, with `phone.js:709-713` injecting a second `rel=manifest` that browsers will not honour. Verified.

**The one strategic point that survives all three critiques — restated correctly:**

11. The project has a rigorous, closed, cross-validated loop for **dot placement** (`.prn` decode, byte-exact tables, ink-area fractions matching `DRIVER_LUTS[4]` to three decimals) and **no loop at all for colour on paper**. That gap is real and it is the largest remaining fidelity risk.

    But the reason is not misallocation, carelessness, or a wrong referent choice. On the evidence in the tree — third-party swatch data, eight monochrome targets, eight identical single-drum `.prn` captures — **the author has one drum and bought the colour data.** The overprint loop was not skipped; it was unavailable.

    Which means the correct next step is not "print a chart." It is exactly what `INK-PHYSICS-PLAN.md` already specifies: *the user* prints the chart on *their* machine with *their* drums, photographs it, and a per-machine ΔLab residual is fitted. All three critiques converged on a recommendation the project had already written down, and then criticised it for arriving late — when the constraint that made it the only viable design is the same constraint that made it impossible earlier.

**What should be dropped entirely:** golden images in March (P1), three-mode consolidation (P2), the `calBlend`-as-worker-port framing (P3), state unification folded into `d087406` (P4), `_isD3D = false` (P5), the npm/test-file indictment (G1), content-hashed assets (G2), and the ISO chart programme as a next step (G4).
